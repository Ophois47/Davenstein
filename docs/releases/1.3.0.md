# Davenstein 1.3.0

Davenstein 1.3.0 expands the project’s native release architecture onto 32-bit x86 Windows and Linux systems while completing the Android touchscreen experience required for normal touch-only play

The release adds native Windows i686 MSVC packaging, Linux i686 GNU cross-compilation, architecture-aware installation and portable packaging, object-format and ABI verification, state-aware visible touch controls, complete menu navigation, touch-driven nonstandard screens, high-score name entry without a keyboard, and a physically verified correction for the Android Application Not Responding condition

Davenstein remains a ground-up Wolfenstein 3-D reimplementation written in Rust with Bevy. The new packages, touch interface, validation systems, and Android corrections described below extend the existing shared Rust application rather than introducing separate gameplay implementations for individual platforms

## Major Highlights

- Added native Windows i686 MSVC releases with both an NSIS installer and portable ZIP
- Added Linux i686 portable releases targeting little-endian 32-bit x86 systems
- Added target-specific i386 native dependency preparation and pre-build linker validation
- Added ELF32 Intel 80386, byte-order, loader, shared-library, checksum, package-content, and extracted-artifact validation
- Added PE32 `IMAGE_FILE_MACHINE_I386` validation for compiled, portable, and installed Windows executables
- Added imported DLL auditing for the Windows i686 executable
- Added architecture-aware NSIS installation through the 32-bit Program Files location and Registry32
- Added silent installation, Start Menu, installed-file, registry-view, and uninstall-cleanup validation
- Added state-aware visible touchscreen controls for gameplay, menus, tap-to-continue screens, and input-disabled states
- Added complete touch-only menu navigation with explicit confirmation and cancellation controls
- Added four-way floating D-pad movement, visible stick feedback, drag-to-turn guidance, action buttons, weapon selection, and pause access
- Added touch and gamepad handling for intermission, game over, cheat messages, and high-score name entry
- Corrected the Android Application Not Responding condition and verified the result on physical hardware
- Added focused touch hit-testing, layout, accessibility, mode-selection, and overlay regression coverage
- Restored direct Unix execution of the committed Android Gradle wrapper

## Linux i686 Cross-Compilation

Davenstein now publishes a Linux i686 portable archive built through Rust’s `i686-unknown-linux-gnu` target

The build uses the maintained i686 cross image and enables Davenstein’s `software_render` feature so the package does not assume a proven target GPU driver. On Apple Silicon hosts, the same amd64 build environment can run through Docker or Colima by explicitly selecting the `linux/amd64` container platform

The Linux i686 workflow is independently selectable for development validation, publishes a dedicated `Davenstein-Linux-i686-Packages` artifact, and is required before a tagged release can be published

## Linux i386 Native Dependency Preparation

A dedicated `scripts/cross_prepare_i686.sh` preparation path installs and validates the 32-bit Linux development interfaces required by Bevy’s windowing, input, audio, and device layers

The target dependency set includes

- Wayland client development files
- ALSA development files
- libudev development files
- X11 development files
- Xcursor development files
- Xi development files
- xkbcommon development files
- Xrandr development files

The preparation path queries every required interface through i386-aware `pkg-config`, links a 32-bit target C probe, and inspects that probe before Cargo is allowed to compile Davenstein

This prevents a nominal i686 build from silently resolving host-architecture libraries or proceeding with incomplete target metadata

## Linux ELF32 Package Validation

The compiled Linux i686 executable is validated independently of the Rust target name

The workflow requires

- ELF32 class
- Little-endian byte order
- Intel 80386 machine identity
- Dynamic linkage through `/lib/ld-linux.so.2`
- Expected declarations for the required Wayland, libudev, ALSA, libgcc, libm, and glibc runtime libraries
- A non-empty executable with executable permissions

The generic Linux portable packager assembles the binary with `assets.pak`, the launcher, portable-storage marker, icon, README, licensing documents, copyright notice, and third-party asset documentation

The completed archive receives a SHA-256 checksum, is extracted into a clean directory, and is checked for its expected contents and executable modes. The extracted executable is then revalidated as little-endian Intel 80386 ELF32 with the same dynamic loader so the uploaded package is proven to retain the ABI established before packaging

## Windows i686 MSVC Build

Davenstein now builds a native 32-bit Windows executable through Rust’s `i686-pc-windows-msvc` target on a Windows Server 2022 release runner

The native MSVC path avoids treating the existing x86-64 GNU package as a substitute for Win32 support. It uses the Windows SDK and C++ x86 build tools available to the runner and produces `Davenstein.exe` directly for the 32-bit Windows ABI

The Windows i686 workflow is independently selectable, publishes a dedicated `Davenstein-Windows-i686-Packages` artifact, and is required before a tagged GitHub Release can be published

## Windows PE32 And Imported DLL Auditing

The original Windows i686 executable is inspected with LLVM COFF tooling immediately after compilation

The workflow requires `IMAGE_FILE_MACHINE_I386` and explicitly rejects AMD64 or ARM64 machine identities. Imported DLL declarations are captured and audited so the package’s runtime dependencies remain visible during release validation

The architecture check is repeated after the portable ZIP is extracted and again after the NSIS installer places the executable in its final installed location

This establishes the same Win32 machine identity across the compiler output, portable release, and installed application rather than trusting only the requested Rust target

## Windows i686 Portable Packaging

The portable Windows i686 ZIP contains

- `Davenstein.exe`
- `assets.pak`
- `README.md`
- Project licensing and copyright documents
- Third-party asset documentation
- `Davenstein.ico`
- `portable.flag`

The presence of `portable.flag` preserves Davenstein’s established portable-storage behavior so save games, high scores, and settings remain beside the extracted application rather than being redirected into an installed application-data location

The archive receives its own SHA-256 checksum, is expanded into a clean validation directory, and is rejected if required files are missing, `assets.pak` is empty, or the extracted executable is not PE32 i686

## Windows i686 NSIS Installation

The Windows installer was made architecture-aware without duplicating the complete NSIS definition

When built with the Win32 release definition, the installer

- Produces an i686-specific filename
- Uses the 32-bit Program Files location, which is `Program Files (x86)` on 64-bit Windows
- Writes application and uninstall metadata through the 32-bit registry view
- Preserves the existing Windows 95-era presentation
- Installs the executable, assets, icon, README, licensing documents, copyright notice, and third-party asset documentation
- Creates all-users Start Menu shortcuts
- Omits `portable.flag` from installed packages

The existing x86-64 installer retains its Program Files and Registry64 behavior when the Win32 definition is absent

## Win32 Registry And Uninstall Validation

The release workflow executes the completed installer silently on a clean native Windows runner

Validation requires

- A clean Program Files (x86) destination before installation
- No pre-existing Davenstein application or uninstall keys in Registry32 or Registry64
- Successful silent installation
- Every required installed file
- A PE32 i686 installed executable
- The expected Registry32 installation and uninstall records
- No corresponding records in Registry64
- The expected release version and installation path
- An all-users Start Menu directory

The installed uninstaller is then executed silently. The workflow waits for removal to complete and rejects the package if the installation directory, Start Menu directory, Registry32 records, or unexpected Registry64 records remain

This validates both installation and cleanup behavior using the actual package delivered to users

## State-Aware Touchscreen Architecture

Touch input is now governed by a shared `TouchUiMode` resource with four explicit modes

- `Gameplay` activates movement, turning, fire, use, weapon, and pause controls
- `Menu` activates a direction cluster with explicit confirm and back controls
- `Advance` converts a deliberate tap into confirmation on screens that only need to continue
- `Off` disables the glass during loading, death-fizzle, or touch-disabled states

The UI layer derives the active mode from the same splash, menu, game-over, intermission, death, cheat-message, and control-lock state used by the application itself

The input source and visible overlay read the same mode and the same `TouchLayout` geometry. A control therefore cannot be visible while inactive or tappable while absent

## Visible Touch Overlay

The touchscreen interface is rendered in window-space through the persistent menu UI camera rather than through Davenstein’s low-resolution gameplay canvas

Gameplay displays

- A floating movement control under the owning thumb
- A visible stick base and knob that reflect the actual clamped movement deflection
- A drag-to-turn hint
- FIRE and USE controls
- Four direct weapon-selection controls
- A MENU control

Menus display a bottom-left direction cluster and right-thumb OK and BACK controls. Confirm deliberately reuses FIRE’s rectangle and back reuses USE’s rectangle so the right thumb keeps the same resting action arc between gameplay and menus

Tap-to-continue screens display an explicit instruction rather than presenting unrelated gameplay buttons

The overlay follows `ActiveInputDevice`: it appears when touch is driving the application and hides when keyboard or gamepad input becomes active

## Four-Way Touch Movement

The floating movement control now behaves as a four-way D-pad rather than an analog stick

After the centre deadzone, the dominant axis wins and emits full cardinal movement

- Horizontal movement strafes left or right
- Vertical movement moves forward or backward
- Diagonal and partial-speed drift are not emitted
- Pushing into the outer ring activates running
- The initial touch position remains the floating origin

This behavior better matches Wolfenstein-style corridor movement while retaining a control that appears beneath the player’s thumb instead of requiring a fixed pad location

Eight-way diagonal movement remains a possible future enhancement rather than part of this release

## Touch Menu Navigation And Safe Confirmation

Touch now contributes through the same `MenuNav` vocabulary used by keyboard and gamepad input

The visible menu cluster maps to

- Up
- Down
- Left
- Right
- Confirm
- Cancel

Menu mode intentionally does not implement tap-anywhere confirmation. A tap must land on the explicit visible OK control before the highlighted item activates, preventing an arbitrary stray touch from selecting destructive actions such as Quit

Gameplay mode exposes only the pause button to the menu accumulator, while input-disabled mode ignores the glass entirely

## Touch-Driven Nonstandard Screens

Screens that exist only to advance now accept touch through `MenuNav.confirm`

This includes

- Initial splash screens
- Score presentation
- Episode victory and end text
- Mission-success intermission
- Game-over presentation
- The active cheat-message modal

The intermission and game-over paths read `MenuNav` after input gathering so they receive the current frame’s gamepad or touchscreen confirmation even while normal player control is locked

The death fizzle and loading states remain touch-disabled so a held or stray finger cannot skip internal transitions

## Touch And Gamepad High-Score Name Entry

High-score name entry no longer requires letter keys

The shared menu controls provide a three-character carousel

- Up and down cycle the current character through A-Z and space
- Right commits the current character and starts the next position
- Left or cancel deletes the current character
- Confirm submits the completed name

Keyboard letter entry remains available. W, A, S, and D keep their letter meaning on this screen instead of being double-consumed as navigation

A newly spawned name-entry screen ignores the same-frame confirmation that dismissed game over, preventing an empty name from being submitted before the player sees the interface

## Android ANR Correction And Physical Validation

Physical Android testing previously produced repeated system Application Not Responding dialogs even while Davenstein could continue rendering or playing

The consolidated Android input work corrected that condition. Subsequent testing on physical hardware verified that the warning no longer recurred while gameplay, rendering, touch controls, menu navigation, and dismissal behavior remained responsive

This release documents the observed and verified outcome without assigning an unsupported internal root cause beyond the completed Android changes

## Touch Geometry And Regression Validation

Touch rectangles are computed in real window pixels and scale within the established UI-scale limits rather than inheriting the 320x240 gameplay canvas

The layout includes accessibility-floor checks for every gameplay and menu target across representative phone, tablet, and desktop sizes

Automated coverage verifies

- Every menu button maps to the correct `MenuNav` bit
- Stray menu taps never confirm
- Gameplay maps only the pause rectangle into menu input
- Advance mode converts a deliberate tap into confirmation
- Off mode ignores every touch
- Gameplay buttons do not overlap one another
- Menu controls do not overlap one another
- Confirm and back retain the FIRE and USE action arc
- The movement region remains clear of the weapon row on narrower tablet layouts
- Weapon rectangles map to the correct one-based slots
- Unmeasured layouts claim no touches
- Touch-disabled states produce no overlay controls
- Screen-state priority selects the correct control mode

The test predicate table uses boxed `MenuNav` readers so the heterogeneous closure types compile as one explicit array. The Android Gradle wrapper is also committed executable for direct Unix invocation

The focused touch test set, complete Rust test suite, debug build, release build, and diff validation completed successfully after the follow-up correction

## Release Workflow Integration

Both new i686 jobs are exposed through the manual release selector and publish architecture-specific workflow artifacts

Tagged release publication now depends on successful completion of both the Windows i686 and Linux i686 package jobs in addition to the previously supported targets

The validation model remains consistent with the rest of Davenstein’s release system

1. Compile for the requested target
2. Inspect the native object format and architecture
3. Build `assets.pak`
4. Assemble the platform package
5. Verify package checksums and required contents
6. Extract or install the completed package
7. Revalidate the executable and platform metadata
8. Exercise removal where the package format supports it
9. Upload only the proven artifacts
10. Require the package before publishing a tagged release

## Compatibility Notes

The Windows i686 packages target the 32-bit MSVC ABI. The installer uses the 32-bit Program Files location and Registry32, while the portable ZIP keeps mutable state beside the extracted application

The Linux i686 package targets little-endian Intel 80386 ELF32 systems and expects `/lib/ld-linux.so.2`. The target system must provide compatible 32-bit Wayland, libudev, ALSA, libgcc, libm, and glibc runtime libraries

The Linux i686 release uses software rendering by default. Performance depends on the target CPU, display stack, and available 32-bit system libraries

The Android public package remains ARM64 `arm64-v8a`. The touchscreen work is implemented in the shared Rust input and UI systems and is therefore not an Android-specific duplicate of gameplay logic

Touch movement is four-way in this release. Eight-way diagonal movement is not yet implemented

The iPhone and iPad host work is a separate future platform milestone and is not part of Davenstein 1.3.0
