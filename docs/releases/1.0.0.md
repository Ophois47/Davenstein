# Davenstein 1.0.0

Davenstein 1.0.0 is the first stable release of Dave Petnick's ground-up Wolfenstein 3-D recreation written entirely in Rust with the Bevy engine

The largest changes are concentrated in the native Rust gameplay systems, including enemy awareness and pursuit, deterministic Wolfenstein-compatible randomness, fixed-timestep simulation, weapon timing, input processing, display and render-target management, widescreen UI composition, persistent settings, world asset reuse, and the complete multi-platform release pipeline

Davenstein does not port, wrap, or execute the original Wolfenstein 3-D C engine. The behavior described below was implemented directly in Rust and integrated into Bevy's ECS, scheduling, asset, rendering, input, and application-state systems

## Major Highlights

- Reconstructed enemy sight, hearing, reaction timing, pursuit, dodging, shooting, damage, ambush, and area-connectivity behavior from the original Wolfenstein 3-D logic
- Moved the simulation to the original 70 Hz tic rate while interpolating presentation for smooth output on modern displays
- Replaced ad hoc random-number generation with the original 256-byte `US_RndT` table through deterministic per-actor Rust components
- Added internal render scaling, selectable exclusive-fullscreen resolutions, a retro 320x240 mode, and a multi-camera presentation architecture
- Rebuilt the classic menu presentation for widescreen displays while preserving a centered 320x200 composition
- Added persistent video, sound, control, and gameplay settings through a debounced RON-backed settings system
- Refined weapon timing, viewmodel animation, keyboard turning, mouselook transitions, and buffered semi-automatic input
- Completed validated release packaging across Windows, Linux, FreeBSD, macOS, x86_64, ARM64, and ARMv7

## Native Rust Simulation and Scheduling

The simulation now runs at 70 fixed updates per second so one Bevy `FixedUpdate` corresponds to one original Wolfenstein tic. This removes the previous AI sub-tic accumulator and lets translated gameplay formulas operate directly in their original timing units while Bevy's fixed-update loop handles catch-up under load

The player camera is interpolated between completed fixed simulation states. Gameplay therefore retains the original 70 Hz cadence without forcing camera presentation to advance in visible 70 Hz steps on 120 Hz, 144 Hz, or other modern displays

Pushwalls were moved onto the same integer-tic model. The vestigial pushwall clock was removed, and movement now advances once per fixed update so pushwall arrival, obstruction, and AI collision checks remain synchronized with the rest of the simulation

The end-of-level tally was also returned to the original rate of one percentage point per 70 Hz step. Kill, secret, and treasure percentages now ratchet at the original cadence and produce the expected decade beeps

## Enemy Awareness and Sight

Enemy awareness was substantially rewritten around the original Wolfenstein actor logic

- `SightPlayer` reaction delays are now class-specific and stored directly on `EnemyAi`
- Guards use `1 + rnd / 4` tics before reacting
- Officers use a fixed two-tic reaction
- Mutants and SS use `1 + rnd / 6`
- Dogs use `1 + rnd / 8`
- Bosses use a one-tic reaction

The sight test now reproduces the original `CheckSight` structure instead of relying on a general-purpose modern field-of-view approximation

- Actors inside the original 1.5-tile `MINSIGHT` square are detected automatically
- Cardinal facings apply the original front-half-plane test
- Diagonal facings remain unrestricted before occlusion testing, matching the original `dirtype` switch behavior
- The final decision still passes through the wall-occlusion trace
- Enemy visibility for shooting uses Bevy's `ViewVisibility`, corresponding to the original renderer's `FL_VISABLE` flag more closely than a hand-tuned angular cone

Gunfire hearing now follows the original `madenoise` and `FL_AMBUSH` rules

- Non-deaf guards can wake from gunfire without direct sight when they occupy an area connected to the player
- Actors placed on `AMBUSHTILE` remain deaf and require sight
- Bosses remain deaf to ordinary gunfire awareness
- The player weapon system publishes a `PlayerNoise` signal into the shared AI data used by sight processing
- Noise state is reset when a new level is constructed

Wolfenstein area connectivity is now represented explicitly in Rust by an area graph built from plane-0 area codes and door links. Only open doors connect areas for player-hearing purposes. This prevents enemies in disconnected map regions from becoming omniscient while preserving the original behavior when doors join those regions

Damage can wake an actor that was not already chasing. Surviving actors play their first-sighting alert bark and retain the wake speed increase even when they are already partway through a tile move. The alert-bark state is persisted through save and load so restoring a game does not incorrectly replay or suppress the actor's state transition

## Enemy Pursuit, Dodging, and Shooting

The previous omniscient breadth-first chase behavior was moved behind the `AI_BFS_CHASE` diagnostic gate, and the normal pursuit path was rebuilt around the original `SelectChaseDir` decision sequence

- The actor evaluates axis-aligned chase directions from the player delta
- Turnaround is avoided unless the fallback sequence requires it
- Directional fallbacks preserve the original preference ordering
- The original north-west-biased sweep can be reproduced through `AI_FAITHFUL_SWEEP_BIAS`
- Door traversal and occupied pushwall tiles are handled explicitly
- Unit tests pin preference order, door behavior, and pushwall occupancy

The original `SelectDodgeDir` combat weave was also restored. An actor with sight of the player can choose randomized diagonal-first movement instead of following a perfect path directly toward the player. The first move after noticing can still reverse direction as required by the original transition rules

`T_Chase` shooting behavior now preempts movement when an armed actor has a valid shot. The probabilistic firing roll is evaluated every tic, engagement range is derived from the same chance formula, and actors remain stationary through their firing states rather than sliding while their attack animation plays. In-flight movement is frozen during the shot and resumes only after the combat state permits it

Enemy spawn and patrol facings were corrected by mapping the original `dirtype` ordering into Davenstein's `Dir8` representation with the proper rotation. Officers and mutants now participate in the same spawn-direction and patrol initialization that previously left them facing south

Actors can no longer plan through or clip across moving pushwalls. Pathfinding and patrol reject occupied pushwall tiles, and the wall's arrival tile is checked again at each movement boundary before it advances

## Original Wolfenstein Randomness

Enemy shooting, reaction delays, player weapon spread, knife attacks, and dog bites no longer rely on separate xorshift and external random generators

Davenstein now contains the original 256-byte `US_RndT` table and advances through it using deterministic Rust state. The first implementation used one shared resource, but the final design assigns a `TableRng` component to each actor and keeps a system-local table state for player weapons

This preserves the original table-driven value distribution while avoiding one globally mutable RNG bottleneck in Bevy's schedule. Actors remain deterministic without forcing otherwise independent AI and combat systems through one serialized resource

## Enemy Hitscan and Damage Fidelity

Enemy hitscan attacks now use a faithful Rust implementation of Wolfenstein's `T_Shoot` behavior instead of player-derived shooting mathematics

- Hit chance varies by tile distance
- A running player receives the original movement adjustment
- The rendered-visibility state participates through the equivalent of `FL_VISABLE`
- SS and Hans retain their original accuracy advantage
- Successful attacks use the original `rnd / 4`, `rnd / 8`, and `rnd / 16` damage bands according to distance

These changes make enemy lethality, missed shots, close-range pressure, and long-range survivability behave according to the original game's actor rules rather than a generic hitscan model

## Weapon Timing and Input Response

The pistol, machine gun, and chaingun viewmodels were retimed and restructured

- The pistol animation now lasts exactly as long as its cooldown
- The pistol becomes fireable on the same tic that the viewmodel returns to ready
- The pistol muzzle flash appears on the firing input rather than several tics after the shot
- The machine gun alternates its two firing frames continuously at an even six-tic cadence while held
- The chaingun alternates its two flash frames at the existing six-tic fire rate without returning to the neutral frame between shots
- The weapon remains visible during the elevator-exit delay before the mission-success screen
- Weapon size follows the 3-D view-window height like the original `DrawPlayerWeapon`, including when the view-size option reduces the gameplay window

Semi-automatic trigger presses are buffered across cooldown boundaries so a click made just before the weapon becomes ready is no longer discarded

Input processing order was corrected so doors, pushwalls, and elevator exits read the current-frame `use_pressed` edge from `PlayerIntent`. This removes intermittent missed use actions caused by systems observing stale input after the gamepad input refactor

Gameplay intent is suppressed while control is locked by menus or modal UI. Fire input is latched across the unlock boundary so closing a menu does not lose the player's intended shot or allow stale movement and use actions to leak into gameplay

Keyboard turning now uses a lower base rate for precise taps and accelerates while running, matching the original run-scaled turning behavior more closely. Disabling mouselook returns the camera pitch to the horizon, including when the options menu holds the normal player-control lock

## Rendering and Display Architecture

Davenstein now renders the 3-D scene into an off-screen world canvas and presents that image through a separate camera. This architecture enables internal scaling without changing the simulation, window dimensions, or menu layout

The display menu exposes internal render scales of Native, 75%, 50%, and 33%. Lower scales reduce the 3-D render workload while nearest-neighbor presentation retains the intended pixel-art character. The system works in windowed, borderless, and exclusive-fullscreen modes, including Wayland environments where monitor mode switching may be unavailable

Exclusive fullscreen now exposes a curated resolution list containing common modes, the monitor's native mode, and a retro 320x240 option. Requested resolutions are resolved to the nearest supported video mode instead of being silently dropped during an existing fullscreen session

Windowed dimensions are set and compared in physical pixels. This prevents non-1x display scale factors from doubling the effective window size or desynchronizing the world color and depth attachments on Windows

World-canvas resizing was made robust across display-mode and resolution changes

- The canvas image is recreated rather than resized in place when attachment compatibility requires it
- Color and depth targets are kept at identical dimensions
- The separate `RenderTarget` component is repointed to the replacement image
- Render-target transitions no longer retain stale attachments that could crash a later render pass

The canvas uses one sRGB render target instead of creating an sRGB view over a UNORM texture. This avoids the `VIEW_FORMATS` capability requirement that is unavailable on some GLES and Broadcom V3D paths

Camera responsibilities are now separated

- The 3-D world camera renders the scene and viewmodel into the world canvas
- A dedicated HUD camera preserves the full canvas for the status bar and border while the view-size viewport reduces only the world and weapon region
- A persistent window-space UI camera renders menus, splash screens, and intermission content independently from the low-resolution world canvas
- Window-UI routing executes before Bevy UI layout so newly spawned menu roots are targeted without a one-frame flash

MSAA is disabled on the 2-D presentation and menu cameras and remains configurable only for the 3-D world camera. This keeps pixel UI sharp and avoids invalid multisample combinations when the setting changes

Tonemapping is disabled and deband dithering is removed from the player camera so the source palette is presented without modern color remapping. Explicit FIFO presentation is requested for vertical synchronization, including borderless X11 and NVIDIA configurations where automatic selection could tear

Desktop wall materials now use back-face culling to reduce fragment work at high resolution. The software-rendering path keeps its separate behavior where that optimization is not appropriate

## Widescreen UI and Classic Composition

Menus were rebuilt to support widescreen displays without stretching the original artwork

- Classic content remains centered inside a 320x200 safe area
- The Options, High Scores, Save Game, and Load Game screens use cropped title plaques matched to the original banner height
- Shared banner bands tile outward to cover widescreen space without scaling the central artwork
- Episode Select, Skill Select, and option menus extend the original red field across side regions instead of leaving black gutters
- Original splash screens remain pillarboxed rather than distorted
- High-score banner borders, top spacing, and banner alignment were corrected after widescreen expansion

The end-of-level overlay is now a top-level UI root rendered through the window-space camera. It is no longer constrained to the reduced gameplay viewport or centered inside the HUD hierarchy

The `Get Psyched` transition was rebuilt around the camera and UI lifecycles

- The previous menu is cleared atomically when loading begins
- The loading screen shares the HUD canvas and level lifecycle
- The panel derives its dimensions from the internal canvas resolution instead of the native window
- The weapon viewmodel returns on the frame control is released
- Red-under-teal flashes, early loading presentation, late viewmodel restoration, and non-native-scale overflow were removed

Level-end bitmap glyph source rectangles use half-texel vertical insets to prevent white separator rows from bleeding into text at fractional presentation scales

## Persistent Settings

Video, control, sound, and gameplay options now persist across launches in `settings.ron`

The implementation is separated into Rust model, storage, and coordination modules. Changes are debounced before writing so rapid menu adjustments do not rewrite the file on every input event. The timer uses Bevy's public completion API and emits one storage write when the debounce period elapses

Installed packages store settings in the current user's application-data location. Portable packages continue to place writable state beneath their local `data/` directory through Davenstein's installed-versus-portable path policy. Flatpak excludes development copies of `settings.ron` from package sources and stores runtime data inside the application sandbox

## World Fidelity and Visual Corrections

Several original map and decoration details were restored

- Wolfenstein object code 124 now spawns the inert dead guard in the opening room of E1M1, restoring the visual explanation for the starting pistol
- Decoration names and sprite mappings were realigned with the original statics
- Missing gibs and blood-pool objects now render instead of producing no entity
- The second gibs object renders upright like an original billboard rather than as a floor decal
- Upright decoration billboards use full wall height so pillars and lamps no longer appear slightly short
- God mode displays the original modal warning, freezes until input, and uses a near-full-width box with centered, thickened text
- Score is withheld while god mode is active, and god mode is cleared when starting a new game

## Rust Asset Reuse and Performance

Decoration spawning now caches `StandardMaterial` handles by plane-1 object code. Every instance of the same static reuses one material instead of allocating an identical material for every map tile, reducing typical level material counts from hundreds to a few dozen

Pickup spawning now uses a level-scoped `PickupAssetCache`

- Meshes are reused by pickup size
- Materials are reused by texture
- The public spawn helper remains a thin wrapper so map spawning, enemy drops, and save restoration continue through the same call path

These changes reduce Bevy asset growth during level construction without changing the gameplay entity model

## Software Rendering and ARM Systems

A dedicated `software_render` Cargo feature can select Mesa llvmpipe as the wgpu adapter for Linux systems without a usable hardware graphics path

The software configuration avoids executing expensive GPU-oriented effects on the CPU renderer. Atmosphere, screen-space ambient occlusion, and environment-map generation are disabled through the storage-texture capability profile, while binding-array and compute limits remain available where Bevy's material and sparse-buffer pipelines require them. CPU light clustering is enabled only for software-render builds; normal desktop builds retain GPU clustering

ARM64 and ARMv7 portable release archives use the software-render feature for Broadcom V3D targets. Low-resolution display and render-scale options provide additional workload control, including 320x240 exclusive fullscreen where the window system supports mode switching and borderless fallback where it does not

The ARM packages are not a claim that Raspberry Pi V3D hardware acceleration is complete. Current Bevy, wgpu, and Mesa behavior still prevents a reliable accelerated Vulkan or OpenGL path on the tested Raspberry Pi configuration. The llvmpipe fallback renders correctly but may remain below the intended playable performance target

## Release Packaging and Reproducibility

The 1.0 release pipeline builds and validates the following packages

| Platform | Architecture | Package |
| --- | --- | --- |
| Windows | x86_64 | Installer EXE and portable ZIP |
| Windows | ARM64 | Portable ZIP |
| Linux | x86_64 | AppImage, portable TAR.GZ, DEB, RPM, and Flatpak |
| Linux | ARM64 | AppImage, portable TAR.GZ, and Flatpak |
| Linux | ARMv7 hard-float | Portable TAR.GZ |
| FreeBSD | x86_64 | Native PKG and portable TAR.GZ |
| macOS | Apple Silicon | Application ZIP |
| macOS | Universal 2 | Application ZIP |

Every public package is accompanied by a SHA-256 checksum

Release and development build scripts use the committed `Cargo.lock` through `--locked` so dependency resolution cannot drift between machines or CI jobs. A centralized release preflight reads the version from `Cargo.toml`, exports it to all package jobs, and rejects a release tag whose version does not exactly match the Rust package version

Flatpak AppStream metadata is generated from the same Cargo release version rather than maintained as a separate hardcoded version list. Dedicated x86_64, ARM64, combined Flatpak, and x86_64 RPM workflow targets allow narrow package validation without rebuilding the complete matrix

The native package jobs perform format-specific validation

- DEB metadata, dependencies, payload layout, executable linkage, installation, and removal are checked on the Ubuntu baseline
- RPM metadata, dependencies, payload layout, `rpmlint`, installation, `rpm -V`, linkage, and removal are checked inside Rocky Linux 9
- Flatpak bundles are built and validated for x86_64 and ARM64
- FreeBSD portable and native packages are validated inside a FreeBSD 14.4 virtual machine
- Windows, Linux, macOS, and ARM archives are opened and inspected for the executable, assets, documentation, licenses, storage mode, and architecture required by each package format

Public package descriptions were standardized across DEB, RPM, FreeBSD, Linux desktop entries, and Flatpak metadata around Davenstein's authorship and native Rust and Bevy implementation

## Compatibility Notes

The macOS application bundles are currently unsigned and not notarized. macOS may require the user to approve the application through Privacy & Security on first launch

Raspberry Pi 5 and Broadcom V3D hardware acceleration remain limited by the current Bevy, wgpu, and Mesa graphics stack. The supplied ARM Linux packages are useful on compatible ARM systems, but the software-render fallback does not guarantee playable Raspberry Pi performance
