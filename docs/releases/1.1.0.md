# Davenstein 1.1.0

Davenstein 1.1.0 adds configurable touchscreen controls, introduces deliberate input-device ownership across touch, keyboard, mouse, and gamepad sources, and substantially reconstructs episode-ending camera behavior in native Rust

This release also restores additional Wolfenstein combat-state behavior, including pain-state lockout, original SS and human boss burst-fire chains, the full knife attack cycle, and melee noise only when an attack connects

Davenstein remains a ground-up Rust application built with Bevy. The input, camera, episode-ending, combat, UI, and settings changes described below were implemented directly in Davenstein's ECS, `FixedUpdate`, rendering, and persistence systems

## Major Highlights

- Added a dedicated touchscreen input source with finger-ID-pinned movement and look roles
- Added configurable touch enablement, look sensitivity, and control size to the Controls menu
- Persisted touchscreen settings through the existing RON-backed settings system
- Added active input-device arbitration so deliberate input determines which source drives gameplay
- Bound gamepad control to one deliberately claimed device and rejected noisy parked analog axes
- Rebuilt episode-ending victory cameras against the original `VictorySpin` and BJ state tables
- Corrected critical Episode 1 and Episode 4 ending failures
- Added scripted-camera ownership so cutscenes cannot be overwritten by player mouselook
- Restored pain-state combat lockout, original burst-fire chains, and the full 24-tic knife cycle
- Improved episode-end navigation, score-screen layout, splash rendering, and weapon-viewmodel recovery

## Touchscreen Input Source

Davenstein now includes a dedicated touch input source integrated with the same `PlayerIntent` pipeline used by keyboard, mouse, and gamepad controls

Touch contacts are assigned stable control roles by touch ID. A finger that begins on the movement region remains responsible for movement, while a finger assigned to the look region remains responsible for turning until that contact ends. This prevents active fingers from exchanging roles when another contact is added, moved, or released

Touch look input controls yaw only. Vertical camera pitch is not modified by touchscreen drag input, preserving a stable first-person view and avoiding accidental upward or downward camera movement during turning

The touch source reports deliberate input through the shared input-device arbitration layer rather than being treated as active merely because a touch-capable display exists

## Touch Layout and Configuration

A dedicated touch-layout system defines the on-screen movement and look regions and scales their geometry for the current presentation size

The Controls screen now exposes three touch options

- Touch enable or disable
- Touch look sensitivity
- Touch control size

The Controls menu dynamically fits its option rows inside the available panel in both its initial spawn path and its cursor-layout update path. Adding the new touch settings therefore does not overflow or misalign the existing controls presentation

Touch configuration is persisted through `settings.ron` alongside the existing video, sound, control, and gameplay settings

Touchscreen support in 1.1.0 applies to compatible builds and touch-capable systems. It establishes Davenstein's input layer for future mobile work, but it does not by itself represent completed Android, iPhone, or iPad packaging

## Active Input-Device Arbitration

Davenstein now tracks the input source that is deliberately driving gameplay through an `ActiveInputDevice` arbitration layer

Keyboard and mouse, gamepad, and touch sources report deliberate activity rather than relying on device presence alone. This prevents an attached but idle device from taking control merely because it exists or continuously reports a neutral or noisy state

Pitch leveling now follows the device actively driving gameplay instead of using touch presence as a proxy. Mouselook and camera-leveling behavior therefore respond to the actual control source rather than the hardware inventory

The arbitration layer gives the input subsystem a single ownership model that can be extended by future WebAssembly and mobile front ends without merging incompatible source behavior into player movement

## Gamepad Ownership and Axis Filtering

Gamepad input is now bound to one device claimed through deliberate player activity

Previously, unrelated attached controllers could contribute axes to the same gameplay frame. Flight sticks, throttles, racing hardware, and other devices with parked non-zero axes could therefore inject phantom movement or turning even when the player intended to use another controller

The new gamepad path adds an axis-sanity gate and requires deliberate input before a device claims control

- One gamepad owns gameplay input at a time
- Parked throttle and flight-stick axes cannot claim control through passive non-zero values
- Unrelated controllers are no longer merged into one movement state
- The active device can change when the player deliberately uses another supported source

This makes normal gamepad behavior more predictable on systems with multiple Human Interface Devices attached

## Episode-End Victory Reconstruction

The episode-ending victory camera was substantially rebuilt inside Bevy's `FixedUpdate` schedule

The new implementation follows the original `VictorySpin` and BJ state tables rather than applying an approximate camera sequence outside the authoritative simulation path. Camera position, facing, movement, and state progression now advance with the same fixed-timestep ownership used by the rest of gameplay

This reconstruction corrects the severe episode-ending failure affecting Episodes 1 and 4. Their victory paths could previously lose the intended scripted camera state through interpolation and axis-detection conflicts

The updated sequence resolves the player and victory orientation from the correct axis relationship and keeps the scripted movement authoritative throughout the ending

## Scripted Camera Ownership

A dedicated `ScriptedCamera` marker now identifies cameras controlled by cutscenes or other authored sequences

Player mouselook and normal camera synchronization skip scripted cameras. This prevents gameplay look state from overwriting the episode-ending victory view or another camera whose transform is owned by a scripted sequence

The marker establishes an explicit ownership boundary between normal first-person camera control and authored camera behavior instead of relying on timing or control-lock side effects

## Camera Interpolation and Death-State Corrections

The death-camera teleport path now collapses the camera interpolation window when the view is moved discontinuously

Without this reset, presentation interpolation could blend from the previous gameplay transform toward the teleported death-camera transform, producing an incorrect intermediate view or allowing old state to reappear for a frame

`LookAngles` are synchronized with the scripted transform at the same transition. The logical camera orientation and rendered transform therefore agree immediately after the teleport

These changes complement the 70 Hz fixed simulation introduced in 1.0.0 by distinguishing normal interpolated movement from intentional camera discontinuities

## Episode-End Navigation and Layout

Episode-ending text screens now support both Escape and forward-page input for leaving or advancing the presentation

The episode score screen reserves status-bar space using the HUD's own scaling rule instead of a separate approximation. Score content and the status bar therefore remain aligned across view sizes and presentation resolutions

The splash presentation now uses its own aspect-preserving canvas dimensions rather than inheriting assumptions from another UI surface. The splash artwork maintains its intended proportions across supported resolutions

The splash version tag uses independent source-pixel insets so its placement remains stable relative to the artwork instead of drifting as output size changes

## Enemy Pain-State Fidelity

Actors displaying a pain frame can no longer shoot, turn, or schedule a new movement step

This restores the state ownership expected by the original actor chains. A pain reaction now temporarily controls the actor instead of allowing chase or combat systems to continue advancing unrelated behavior underneath the visible pain state

Once the pain state completes, normal movement and attack scheduling resume through the actor's subsequent state transition

## SS and Human Boss Burst Fire

SS enemies and human bosses now execute multi-shot volleys through a `BurstFire` sequence rather than treating their attacks as a single generic hitscan event

Burst shot counts, spacing, wind-up, and post-volley recovery are derived from the original `s_ssshoot` and `s_bossshoot` state chains

- Each volley queues the number of shots represented by the original chain
- Inter-shot spacing follows the state timing rather than a hand-tuned constant
- The initial wind-up is incorporated into the complete attack timing
- `shoot_cd` extends across the entire volley so another attack cannot begin before the state chain finishes

This preserves the distinct firing cadence of SS and human boss actors while keeping the implementation integrated with Davenstein's Rust combat scheduling

## Knife Timing and Noise

The knife now uses the complete four-stage `attackinfo` cycle for a total cooldown of 24 tics instead of the previous 10-tic approximation

The longer cycle aligns attack availability with the viewmodel and combat-state sequence rather than allowing another knife attack before the original chain would have completed

A landed knife hit now raises `PlayerNoise` through the same combat processing path used for successful damage. This matches the original `madenoise` behavior at the start of `DamageActor`

A missed knife swing remains quiet. Noise is generated only when the melee attack connects and damage processing actually occurs

## Weapon Viewmodel Recovery

The weapon viewmodel is repainted inside the first-frame guard of `weapon_fire_and_viewmodel`

A `HudState` reset that occurs while gameplay is locked can no longer leave a stale idle sprite displayed after the state transition. The image is refreshed from the current weapon and animation state when the system resumes ownership

This corrects a presentation error without changing weapon timing or combat results

## Persistent Settings

The settings model now includes the touchscreen configuration required by the new input source

- Touch enabled state
- Touch sensitivity
- Touch control size

The values use the same installed-versus-portable storage policy as Davenstein's existing settings. Installed packages use the platform application-data location, portable packages use their local `data/` directory, and Flatpak uses its sandboxed application-data location

## Rust Architecture

The 1.1.0 work extends Davenstein's existing source-oriented architecture rather than adding a platform-specific input bypass

- Touch input implements the shared source interface
- Deliberate activity feeds one arbitration model
- All active sources resolve into `PlayerIntent`
- Scripted cameras carry explicit ECS ownership
- Victory and death-camera changes run through fixed simulation and interpolation state
- Burst fire is represented as scheduled combat state
- Touch configuration uses the existing typed settings model and RON store

This keeps future browser and mobile work aligned with the desktop input and gameplay systems instead of creating separate control logic for each platform

## Compatibility Notes

Touchscreen controls require a touch-capable system and a build whose windowing backend delivers touch events

The new touchscreen input layer does not change Davenstein's current package support matrix. Windows, Linux, FreeBSD, and macOS remain the published desktop targets for 1.1.0

Android, iPhone, iPad, and WebAssembly packaging remain future platform work

Raspberry Pi 5 and Broadcom V3D hardware acceleration remain subject to the current Bevy, wgpu, and Mesa limitations documented in the README

The macOS application bundles remain unsigned and not notarized
