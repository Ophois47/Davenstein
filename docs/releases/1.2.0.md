# Davenstein 1.2.0

Davenstein 1.2.0 extends the project’s native Rust and Bevy architecture onto Android, adds Linux RISC-V 64 and PowerPC64LE release targets, and establishes signed and notarized macOS distribution for Apple Silicon and Universal 2 systems

This release refactors application startup so the desktop executable and Android `NativeActivity` host enter the same library-owned Bevy application graph. Platform-specific launch, filesystem, packaging, signing, and ABI requirements are handled at the host boundary while gameplay, rendering, input, persistence, assets, resources, plugins, and schedules remain implemented by the shared Rust codebase

Davenstein remains a ground-up Wolfenstein 3-D reimplementation written in Rust with Bevy. The mobile integration, cross-compilation targets, ELF validation, Apple signing pipeline, game-over corrections, death fizzle, weapon behavior, and release automation described below were implemented directly in Davenstein’s Rust application structure and supporting build systems rather than through a port or wrapper around a legacy engine

## Major Highlights

- Added a playable native Android ARM64 build using Android `NativeActivity` and the shared Rust application library
- Added a signed Android APK release pipeline with permanent-key signing, signer verification, package inspection, embedded-asset validation, and 16 KiB ELF page compatibility
- Refactored desktop and mobile startup into one library-hosted Bevy application entrypoint
- Added Linux RISC-V 64 portable releases targeting RV64GC systems with the LP64D double-float ABI
- Added Linux PowerPC64LE portable releases targeting the little-endian OpenPOWER ELF V2 ABI
- Added automated target-library sysroot preparation for PowerPC64LE without installing foreign glibc packages into the build container
- Added Developer ID signing, Apple notarization, stapled tickets, and Gatekeeper verification for macOS packages
- Added signed Universal 2 macOS application archives containing both Apple Silicon and Intel executable slices
- Replaced the death-screen alpha wash with an opaque pixel dissolve modeled after Wolfenstein 3-D’s fizzle fade
- Corrected game-over overlay camera ownership, full-window presentation, menu reconstruction, and same-frame input transitions
- Restored Wolfenstein-style switch-up-only weapon pickup behavior
- Improved the Windows GNU cross toolchain and rebuilt the NSIS installer around a Windows 95-era presentation

## Shared Rust Application Entrypoint

Davenstein startup is now owned by a shared Rust application module rather than being constructed directly inside the desktop executable

The Bevy `App`, plugin registration, resources, states, schedules, systems, and application-owned modules were moved from `src/main.rs` into the reusable application path in `src/app.rs`. The desktop binary is consequently reduced to a native host that enters the same application implementation exported to other platforms

The package now produces both Rust and C-compatible library forms

- The `rlib` output supports normal Rust linkage and desktop development
- The `cdylib` output produces the Android native library
- The desktop `Davenstein` binary remains a normal executable target
- `pak_builder` remains a separate native build-time utility

This separation establishes an explicit boundary between platform launch mechanics and the game itself. Android does not contain a second implementation of Davenstein’s gameplay or Bevy setup; it loads the same Rust-owned application graph used by the desktop executable

## Android NativeActivity Host

The Android build launches Davenstein through Android’s native application model and packages the Rust library as `libdavelib.so`

The Android manifest declares the native activity and identifies the Rust shared object loaded by the platform. Android lifecycle entry reaches the library-hosted application entrypoint, allowing Bevy and Davenstein’s existing systems to initialize without a Java or Kotlin gameplay layer

The Android host uses the existing touch-input pipeline introduced before mobile packaging was completed. Finger-ID-pinned movement and look ownership, deliberate active-input arbitration, touch sensitivity, control sizing, and persisted touch settings therefore remain part of the same typed Rust input model used on desktop touch-capable systems

The mobile host does not fork player movement, combat, UI, or settings behavior into an Android-specific implementation

## Android Assets and Persistent Storage

The Android package embeds Davenstein’s generated `assets.pak` and its SHA-256 digest inside the APK assets

At startup, the Android path layer resolves the package-provided asset source and the application’s writable private storage. Packaged content is made available to the same Rust asset-loading systems used by other platforms while save games, high scores, options, and other mutable state remain inside the application’s private Android data location

Application path discovery was made safe for Android lifecycle use rather than repeatedly depending on transient platform state. Resolved writable paths can be cached after the native activity provides them and subsequently consumed by Davenstein’s existing storage systems

The installed Android package therefore preserves the project’s established storage distinction

- Immutable packaged content remains part of the APK
- Mutable application state uses Android-private persistent storage
- Desktop installed packages continue using platform application-data directories
- Portable desktop packages continue using their local `data/` directories
- Flatpak continues using its sandboxed application-data location

## Android ARM64 Release Pipeline

The public Android release targets `arm64-v8a` through Rust’s `aarch64-linux-android` target

The release workflow centralizes Java, Android command-line tools, SDK, NDK, build-tools, minimum API, Gradle, Android Gradle Plugin, Rust target, and `cargo-ndk` requirements rather than depending on an individual workstation’s ambient configuration

`cargo-ndk` builds the Rust library for the configured Android minimum API and stages the resulting `libdavelib.so` beneath the ABI-specific JNI library directory consumed by Gradle

Before packaging, the workflow inspects the native library with ELF tooling and requires

- ELF64 class
- AArch64 machine identity
- A non-empty shared object
- Every loadable segment to use an alignment compatible with 16 KiB Android page sizes

The alignment check evaluates every ELF `LOAD` program header and rejects a native library whose alignment is smaller than `0x4000` or not an exact multiple of that boundary

Gradle then assembles an unsigned release APK containing the Rust library and generated asset pack. The workflow reconstructs a temporary runner copy of the permanent Android signing keystore, verifies the keystore against its configured SHA-256 digest, aligns the APK before signing, and signs it with the configured release identity

The completed package is verified with Android build tools rather than accepted solely because the signing command returned successfully

- `apksigner` validates the APK signature and reports the signing certificate
- The signer certificate digest must match the expected release certificate
- Package identity and version metadata are inspected from the APK
- The archive must contain exactly the intended ARM64 native library
- The packaged native library is re-extracted and revalidated as AArch64 ELF64
- `assets.pak` and its digest are extracted and integrity-checked
- The finished APK receives its own `.sha256` release checksum

The Android workflow can run independently for development validation and can also consume the exact commit proven by the main tagged-release workflow before publishing the APK for that release

## Linux RISC-V 64 Cross-Compilation

Davenstein now publishes a Linux RISC-V 64 portable archive built from an x86-64 GitHub Actions runner

The Rust target is `riscv64gc-unknown-linux-gnu`, selecting the general-purpose RV64GC instruction profile and the LP64D double-float ABI. The target-specific `Cross.toml` preparation installs the native Linux development interfaces required by Bevy and its windowing, input, audio, and device layers inside the cross-compilation environment

The build enables Davenstein’s `software_render` feature so the release does not assume the availability of a proven target GPU driver

The resulting executable is inspected independently of the Rust target name. The workflow requires

- ELF64 class
- RISC-V machine identity
- RVC compressed-instruction support in the ELF flags
- The double-float ABI flag
- The LP64D dynamic loader at `/lib/ld-linux-riscv64-lp64d.so.1`

The generic Linux portable packager assembles the executable, `assets.pak`, launcher, portable-storage marker, icon, README, licensing documents, copyright notice, and third-party asset documentation into the RISC-V archive

The archive checksum is verified, its contents and executable modes are inspected after extraction, and the extracted executable is rechecked for the RISC-V LP64D ABI and loader before the package can be uploaded or satisfy a tagged release

## Linux PowerPC64LE Cross-Compilation

Davenstein now publishes a Linux PowerPC64LE portable archive targeting little-endian 64-bit PowerPC systems using the OpenPOWER ELF V2 ABI

The Rust target is `powerpc64le-unknown-linux-gnu`. The maintained `cross` image provides the compiler and base glibc sysroot but does not provide the complete set of target-architecture libraries required by Bevy’s Linux platform integration

A dedicated preparation script constructs the missing target environment without installing foreign PowerPC glibc packages into the container’s native amd64 package database

The preparation path

- Registers Debian’s `ppc64el` package architecture
- Configures Ubuntu Noble Ports for PowerPC packages
- Downloads the required development packages without installing them
- Reads each package’s declared architecture before extraction
- Ignores unrelated host-architecture packages
- Explicitly excludes the foreign `libc6:ppc64el` package
- Extracts selected package payloads with `dpkg-deb`
- Consolidates target headers, libraries, and `pkg-config` metadata into the PowerPC64LE sysroot

The extracted target environment includes the Wayland client, ALSA, libudev, X11, Xcursor, Xi, xkbcommon, and Xrandr interfaces required by Davenstein’s Bevy configuration

Before Cargo is allowed to build Davenstein, the script queries every required target package through the isolated PowerPC64LE `pkg-config` directory and links a target-architecture C probe with the complete native library set

The probe must identify as

- ELF64
- Little endian
- PowerPC64
- OpenPOWER ELF V2 ABI
- Dynamically linked through `/lib64/ld64.so.2`

This pre-link proof prevents a build from proceeding with host libraries, incomplete metadata, an incorrect endian variant, or an invalid PowerPC ABI

The final Rust executable is independently inspected for its ELF class, byte order, PowerPC64 machine identity, OpenPOWER ELF V2 ABI, dynamic loader, and expected shared-library declarations

After portable packaging, the extracted archive is inspected again so the uploaded executable is proven to retain the same architecture, ABI, loader, executable permissions, assets, launcher, portable marker, and documentation validated before packaging

## macOS Developer ID Signing and Notarization

Davenstein’s macOS packages are now signed with a Developer ID Application identity and submitted to Apple’s notarization service

The release workflow creates an ephemeral CI Keychain, imports the signing identity and required certificate chain, configures Keychain access for non-interactive signing, and removes the temporary Keychain during cleanup even when an earlier build or notarization step fails

Bundle construction, archive creation, signing, notarization, and verification are implemented as separate guarded scripts rather than one opaque packaging operation

The signing path validates the application structure before applying the final signature. Bundle resources are placed inside the signed application hierarchy, the main executable is signed with the hardened runtime and a secure timestamp, and the outer application bundle is sealed only after its executable and resources are in their final locations

The signed archive is submitted to Apple and must receive an accepted notarization result. The returned ticket is stapled to the application before the release archive is finalized

The finished ZIP is extracted into a clean verification location and the extracted application is checked again using Apple’s native signature, stapler, and Gatekeeper tooling

This verifies the artifact that users actually download rather than only the pre-archive working directory

## Universal 2 Assembly and Signature Ownership

The Universal 2 package combines independently built Apple Silicon and Intel Rust executables into one Mach-O universal binary

The architecture inputs are inspected before combination and the resulting executable must contain both `arm64` and `x86_64` slices

Mach-O signature metadata inherited from intermediate inputs is removed before the final universal executable is assembled. The workflow verifies that the intermediate universal binary remains unsigned before bundle signing begins

This prevents stale or slice-specific signature metadata from being carried into the final application and establishes one unambiguous signature owner for the completed Universal 2 bundle

The assembled application is then signed, notarized, stapled, archived, extracted, and Gatekeeper-verified through the same final-artifact path used by the Apple Silicon package

## Death Fizzle Reconstruction

The previous translucent death-screen wash has been replaced with an opaque pixel dissolve modeled after Wolfenstein 3-D’s fizzle fade

The effect mutates the generated dissolve image through Bevy’s asset system and progressively replaces the visible game image at pixel granularity rather than applying one uniform alpha value over the complete frame

The dissolve is fully opaque as pixels are selected, preserving the visual character of the original transition instead of leaving the underlying frame continuously visible through a translucent overlay

When the death sequence reaches game over, the presentation completes from red to solid black so the game-over text and subsequent menu are rendered against a stable black background

The transition remains integrated with Davenstein’s Rust-owned HUD, image assets, and state progression rather than being implemented as an external video or platform effect

## Game-Over UI Camera Ownership

The game-over overlay now renders as a top-level UI root assigned to the full-window menu camera

Previously, the overlay could inherit the reduced gameplay-canvas presentation path and appear shrunken within the rendered world surface. The corrected hierarchy separates full-window game-over presentation from the canvas used to preserve the game viewport’s scaling and aspect behavior

The overlay’s root ownership and target camera are now explicit, matching the application’s other full-screen menu surfaces

This prevents the game-over presentation from depending on incidental entity ancestry or whichever camera happened to resolve the inherited UI target

## Game-Over Menu Reconstruction

The menu system now compares its rendered row count with the currently active action list

When game-over state changes the available actions, a stale menu whose entity rows no longer match the logical action vector is rebuilt. This ensures actions such as Quit remain reachable rather than leaving the cursor attached to an obsolete menu layout

The game-over transition also guards newly spawned menu state against the same-frame Enter press that dismissed the preceding overlay

Without this guard, one `just_pressed(Enter)` event could both leave the game-over presentation and immediately activate the default item in the newly created menu, stranding the player in episode selection or initiating an unintended action

The new `just_spawned` ownership rule requires the replacement menu to survive its creation frame before accepting activation input

## Weapon Pickup Fidelity

Weapon pickups now follow Wolfenstein 3-D’s switch-up-only selection behavior

A newly acquired weapon is automatically equipped only when it outranks the best weapon the player already owns. Picking up a lower-ranked weapon can still add the weapon or ammunition without replacing a stronger active weapon

This corrects cases such as collecting a machine gun while already carrying the chaingun, which previously could downgrade the player’s selected weapon

The rule is evaluated from owned weapon rank rather than only comparing the pickup with the currently displayed sprite, keeping inventory state and viewmodel selection synchronized

## Windows GNU Cross-Compilation

The Windows x86-64 release continues to be cross-compiled from Linux through the GNU target, but the toolchain path now validates its linker before compiling Davenstein

The maintained cross image was updated to provide a sufficiently recent MinGW-w64 Binutils toolchain. The workflow extracts the linker version and requires Binutils 2.40 or newer before building the Rust executable

This prevents older GNU COFF tooling from misinterpreting emitted directives and overflowing the Windows export ordinal table during the final link

The resulting portable executable is inspected as PE32+ x86-64 after packaging, and the Windows ARM64 path independently verifies `IMAGE_FILE_MACHINE_ARM64` for its MSVC-built executable

## Windows Installer Presentation

The NSIS installer now uses a deliberately Windows 95-era presentation

The installer disables themed controls and applies classic system presentation choices including

- MS Sans Serif-style typography
- A dark-blue setup backdrop
- Traditional Windows system colors
- Segmented progress presentation
- Period-appropriate control labels and layout

A Win32-only NSIS string-trimming modifier that prevented the installer script from compiling correctly on Linux release runners was removed. The visual treatment therefore remains compatible with the automated cross-platform packaging environment used to produce the public installer

## Dependency and Build Reproducibility

Davenstein no longer tracks the repository-root `Cargo.lock` or requires `--locked` for normal project builds

This matches the project’s library-hosted architecture and avoids making platform builds depend on a stale lockfile generated by a different host or target configuration

The release system distinguishes project dependency resolution from externally installed build tools

- Davenstein builds do not require the removed repository lockfile
- The Flatpak path generates the transient dependency lock data required for offline Cargo source vendoring
- The external `cross` utility remains pinned to version 0.2.5 and is installed with its own upstream lockfile
- Android tool versions are declared centrally in committed configuration and workflow constants
- Tagged builds require the Git tag version to match `Cargo.toml`

This keeps release inputs explicit without treating one generated project lockfile as valid for every operating system, architecture, and packaging environment

## Release Validation Architecture

The release workflows validate package identity at multiple boundaries rather than treating successful compilation as sufficient proof

The general pattern is

1. Build the Rust executable or shared library for the requested target
2. Inspect its native object format and architecture
3. Build the generated `assets.pak`
4. Assemble the platform package
5. Verify its checksum
6. Extract or inspect the completed package
7. Revalidate the executable, shared library, assets, permissions, metadata, and required documentation
8. Upload only the proven package
9. Require supported platform jobs before publishing a tagged GitHub Release

Target-specific validation includes

- PE and COFF machine checks for Windows
- ELF machine, ABI, endian, flag, and loader checks for Linux cross targets
- Native installation and removal for DEB, RPM, Flatpak, and FreeBSD packages
- AArch64 and 16 KiB load-segment checks for Android
- APK package, signer, asset, and native-library inspection
- Mach-O architecture, code-signature, notarization, stapling, and Gatekeeper checks for macOS

The release version remains authoritative in `Cargo.toml`, and tagged release publication is rejected if the Git tag and Rust package version disagree

## Rust Architecture

The 1.2.0 work extends Davenstein’s existing Rust architecture across additional operating systems and processor families rather than creating independent platform ports

- The Bevy application graph is owned by a shared Rust library entrypoint
- Desktop and Android hosts enter the same plugins, resources, states, and schedules
- Android exports the Rust application as a `cdylib`
- Platform paths are resolved behind the shared storage interfaces
- Touch input continues through the common `PlayerIntent` and active-device arbitration systems
- Generated assets remain in Davenstein’s existing packed-asset format
- Mobile lifecycle requirements are isolated from gameplay ownership
- Cross targets use the same Rust gameplay and presentation code
- ELF and Mach-O ABI properties are proven after compilation and again after packaging
- Signing identities are introduced only at the final platform packaging boundary
- Game-over and death-presentation corrections remain normal Bevy ECS and asset-system behavior

This keeps Android, RISC-V 64, PowerPC64LE, Intel macOS, Apple Silicon macOS, Windows, Linux, and FreeBSD aligned with one native Rust implementation

## Compatibility Notes

The Android release targets 64-bit ARM devices using the `arm64-v8a` ABI. Android x86-64 remains useful for development and emulator work but is not published as a public 1.2.0 package

The Android package requires a device and operating-system version compatible with the minimum SDK declared in the committed Android configuration. The native library is validated for devices using 16 KiB memory pages

The RISC-V 64 package targets RV64GC Linux systems using the LP64D double-float ABI and expects `/lib/ld-linux-riscv64-lp64d.so.1`

The PowerPC64LE package targets little-endian 64-bit PowerPC Linux systems using the OpenPOWER ELF V2 ABI and expects `/lib64/ld64.so.2`

The RISC-V 64 and PowerPC64LE releases are portable archives rather than distribution-native packages. Their target systems must provide compatible Linux runtime libraries required by the executables

The RISC-V 64 and PowerPC64LE packages use Davenstein’s `software_render` feature and do not imply working hardware acceleration on every target system

The macOS packages require macOS 11 or newer. The Universal 2 package contains both Apple Silicon and Intel executable slices, while the smaller Apple Silicon package contains only the native ARM64 build

The macOS applications are signed, notarized, stapled, and intended to pass Gatekeeper without requiring a manual security override

Raspberry Pi 5 and Broadcom V3D hardware acceleration remain subject to the current Bevy, wgpu, and Mesa limitations documented in the README
